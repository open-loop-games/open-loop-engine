# CLAUDE.md

Open Loop Engine — headless incremental game substrate. The surface grows from real consumer pressure, continuously and selectively — never a one-time extraction, and never a promise to absorb every gap a consumer reports.

**Stack:** TypeScript + Vue 3 (reactivity only) + break_eternity.js (`Decimal` for all game quantities — no plain `number`) + nanoevents + Vitest.
**Peers:** not bundled — consumers own the versions. `peerDependencies` in `package.json` is the list.
**Entrypoints:** `@open-loop/engine` (full surface), `/primitives`, `/core`, `/systems`, `/harness`, `/types` (types-only). The package is `@open-loop/engine`; `open-loop-engine` is the repo.
**Functional core:** Pure evaluation (conditions, effects, formulas) separated from reactive state (resources, persistent refs). Headless runner proves it — same engine logic runs with or without a browser.

## Start here — API surface

Before assuming the engine lacks a primitive, or hand-rolling a pattern that should already exist: **route through `docs/api/INDEX.md`, then read the routed tier's `## Canonical entrypoints` block.** INDEX.md is routing — Task table (verb), Concept index (noun), Cluster directory (subsystem), Tier map — pointing into the per-tier files that hold the actual symbols. Its Tier map is the tier list; both it and the tier files are generated, so read them rather than a copy kept here. The tier file's `Canonical entrypoints` block is the load-bearing read; per-symbol entries underneath give `name:line` into source.

Symbol-grepping for names you arrived with confirms expectation and misses adjacent surface — and the resulting hand-roll gets reported as an engine gap when it was a reading failure. Route from the task, don't grep from the vocabulary.

- `docs/api/INDEX.md` — router. Task table / Concept index / Cluster directory / Tier map, plus reserved-name and predicate-form disambiguators. Generated by `pnpm build:api`; editing by hand is meaningless.
- `docs/api/<tier>.md` — per-tier directory with a `## Canonical entrypoints` block. Read this for the routed tier before writing code.
- `docs/consumer-guide.md` — narrative thinking model: levels of abstraction, persistence, modifier chains, when the engine should grow.

## Commits

Conventional commit prefixes — `release-it` picks the bump from accumulated commits at cut-point. Pre-1.0 (`preMajor: true`), `feat!:` / `BREAKING CHANGE:` bump MINOR, not MAJOR — breaking changes are expected in 0.x.

- `feat:` — new public API (MINOR bump)
- `fix:` — bug fix (PATCH bump)
- `refactor:` / `perf:` — internal change, no API surface change (PATCH bump)
- `feat!:` / `fix!:` or `BREAKING CHANGE:` in body — breaking API change (MINOR pre-1.0, MAJOR after)
- `chore:` / `docs:` / `test:` — no version bump

Releases are manual and batched: `pnpm exec release-it` at a cut-point bumps version, regenerates `CHANGELOG.md`, commits, tags. `.release-it.json` keeps it local (`push: false`, `npm.publish: false`); `pnpm publish` is a separate step (`publishConfig.access` is `public`, so no `--access` flag needed).

**First cut (0.1.0):** `package.json` already sits at `0.1.0` with no tags, so a plain `release-it` would bump *past* it and prepend a generated section above the hand-curated `0.1.0` entry. Cut the first release with `pnpm exec release-it --no-increment` to tag `0.1.0` as-is and keep the curated CHANGELOG. Subsequent releases run plain `release-it`.

### Publish surface

`npm pack --dry-run` prints the exact tarball and is the check to run before publishing — `files` is the allowlist that decides it, and a path named there **cannot** be re-excluded by `.gitignore`. Hence the globs: `docs/*.md` + `docs/api` rather than a bare `docs`, which would publish any gitignored working files sitting under it. `src` ships because every `docs/api/` entry ends in a `src/path:line` pointer — the two travel together or those pointers dangle in an installed copy. `exports` still admits only the declared subpaths, so shipped source is reference material, not an import surface. `prepublishOnly` rebuilds, so shipped docs always describe the shipped `dist`.

`declarationMap` is on, which makes IDE go-to-definition land in that shipped source instead of a `.d.ts`. It survives `tsc-alias` because rewriting an import specifier changes a column, never a line — but the build order is load-bearing, so re-verify mappings if that step ever moves.

Scope is optional but encouraged: `feat(systems):`, `fix(core):`, etc.

### Breaking-change entries

When committing a `feat!:` / `fix!:` or a change with `BREAKING CHANGE:` in the body, include both the consumer-side migration and the maintainer-side rationale inline in the commit body. `release-it` lifts these into `CHANGELOG.md` verbatim, so one surface serves both audiences — no separate migration doc, no parallel "removed things" ledger.

```
feat(core)!: replace Action primitive with Sequencer + task lookup

BREAKING CHANGE: `createAction` is removed. Consumers wire a Sequencer
directly and look tasks up via an id→task map.

Migration:
  // before
  const action = createAction({ id: 'chop', ... })
  // after
  const sequencer = createSequencer()
  const tasks = { chop: { ... } }
  sequencer.enqueue('chop')

Why removed: Action was a god-function whose lifecycle/serialization/cursor
concerns couldn't be untangled without reinventing Sequencer internally.
Killed after the starter stress test showed three games each working
around a different part of it. Don't reintroduce a generic Action —
the composition is the primitive.
```

Keep the Migration block short enough to paste into a consumer PR, and keep the Why block specific enough that future-you doesn't re-derive the primitive. When a breaking change is obvious (e.g. a rename), skip both blocks — the ceremony is only worth it when it's non-obvious.

### Type-surface pins

`tests/types/public-api.test.ts` pins the inferred types of key factories (`createEngine`, `createResource`, `createSkillCategory`, `EngineContext.inject`, etc.) via vitest's `expectTypeOf`. These are enforced by `pnpm typecheck` — a refactor that silently widens a generic, drops an overload, or loses a literal type fails there instead of surfacing in a consumer weeks later. When a pin fails intentionally, update the expectation in the same commit as the source change.

## Architecture

Five layers, strict one-way dependency:

```
primitives  →  core  →  systems  →  modules (consumer-provided)
                                 ↘  harness  (headless-sim substrate, optional)
```

```
src/
├── primitives/    # Zero deps, no Vue. Foundational types, Decimal, RNG.
├── core/          # Vue reactivity enters. Generic composable primitives — no game-pattern opinions.
├── systems/       # Registration surfaces over core — one per validated incremental pattern.
├── harness/       # Headless-sim substrate: runners, probes, walker, picker, perturbation, solver. Game code never imports it; balance tooling does.
├── engine.ts      # Engine assembly — the module-system façade composing core + systems. `createEngine()` lives here.
├── reactivity-reexports.ts  # Vue reactivity surfaced through the engine. Consumers import these, not `vue` — a separately-resolved `vue` won't subscribe to engine refs, and updates silently miss.
└── index.ts       # Barrel — the public surface.
```

### Layer Rules

- **Primitives** imports nothing from core, systems, or harness
- **Core** imports from primitives only
- **Systems** imports from primitives and core only
- **Harness** imports from primitives, core, and systems — sits above systems, below consumers; game modules never import it
- **Modules** (consumer-provided) import from any engine layer

### Layering Principle

**Core = generic composable primitives.** No opinions, no game patterns. Sequencer stores string IDs. TickDriver ticks. Resources hold reactive Decimals. Modifier chains evaluate. Persistent refs serialize. These compose freely and never force a particular game shape.

**Systems = registration surfaces over core.** Each system encodes a known incremental game pattern as a typed registration contract: accept definitions via a typed registry, create the right engine primitives per definition (persistent context, Skill, Purchasable, etc.), expose accessors (getDef, getInstance, getState), and provide mod extension points (registry.patch). Game authors describe *what* their content looks like (mapSkill, mapPurchasable); the system handles *how* it becomes live engine objects. `createSkillCategory` is the reference implementation. Systems never lock consumers out of core — if a system doesn't fit, drop down to the primitives it composes and wire manually.

**Modules = consumer-provided game content.** Import from any engine layer. The 20% that varies too much to standardize (specific formulas, UI behavior, game-specific action types) lives here.

The test: if you'd copy-paste the same wiring between two different incremental games, it belongs in systems. If it only makes sense for one game's design, it's a module. If it has no opinion about game design at all, it's core.

## Code Rules

**Naming:**
- Functions: `verbNoun` — `createResource`, `evaluateCondition`
- Types: PascalCase — `IResource`, `GameStateAccessor`
- Files: kebab-case.ts
- Factories: `create*()` pattern
- Standard verbs: `getX` aggregator, `isX` type guard, `formatX` formatter, `setupX` wiring. Noun-form (`multiplicativeEffect`, `replacementBinding`, `fractional`) is the carve-out for helpers consumed declaratively as configuration data.

**Code markers:**
- `TODO(expansion)` — validated pattern, deferred until a consumer needs it. Three lines max, co-located with the code it would change.
- `TODO(ergonomics)` — working but verbose path; simplify when the pattern recurs in two+ consumers.
- See `PROCESS.md` § Parked patterns for rationale and graduation rules.

**Content-unit factories:** Factories accepting `id?: string` resolve identity in order — explicit argument, ambient `withPersistentContext` id, auto-counter (tests only).

**Section banners:** `// === UPPERCASE ===` short-form, one line per section. Inner factory-body sub-sections use the same form at deeper indent. Skip banners on files small enough that scrolling isn't an issue.

**Type guards:** all engine primitives — content-unit factories and structural-shape primitives alike — discriminate via structural shape (`instanceof`, `'prop' in x`, class identity, presence of a discriminator field on the runtime object). No `*Type` symbol exports, no branded `isType(x, XType)` guards. When a narrow is genuinely needed at a callsite, inline a one-line type predicate next to the code that needs it (`const isAccumulator = (s: Skill): s is AccumulatorSkill => s.permanentBonus != null;`) rather than exporting a guard from the system.

**Systems-layer factory decomposition:** large `create*` factory bodies in `src/systems/` decompose under `// === SECTION ===` banners with this order — TYPES, CONSTANTS, PRIVATE BUILDERS (`buildX` helpers), PRIVATE TICK (`tickX(ctx, dt)` over a typed `XTickContext`), FACTORIES (public, orchestration-only), PUBLIC UTILITIES (`getX`/`formatX`/`setupX`). Factory body itself follows the ladder: id + context push → state refs → context pop → options destructure → defaults resolve → builder calls → wire object literal + return. Ad-hoc computation between builder calls is a missing builder. Pure helpers that aren't factory concerns live in a sibling file (`auto-purchase.ts` beside `purchasable-category.ts`; `recommendation-strategies.ts` beside `recommendation.ts`; etc.). `createSkillCategory` is the reference implementation. Builders are private functions, not classes; factory tests cover the seam, not isolated builder unit tests.

**Decimal arithmetic is neither exact nor total.** Work in the coordinate where the value is defined and the precision lives, rather than evaluating into a domain edge and inspecting the result: solve above layer 0 in log space, take integer roots with `integerRoot`, build integer powers by multiplication, and never verify an answer by raising it back through `pow` (that direction multiplies the stored exponent's ulp by the degree where the root divides it). `Decimal` answers plausible finite numbers for undefined inputs — `pow(0, -1)` is `0` — so "no NaN escaped" is not a correctness check. Any assumption that an operation is exact gets a law.

**Must:**
- Type all public API explicitly
- Keep layers one-way (primitives → core → systems → harness; modules import from any)
- Pure functions for evaluation, reactive refs for state
- Test with Vitest, TDD preferred

**Must Not:**
- Import Vue in primitives layer
- Import systems from core
- Add UI components, rendering, or game-specific content
- Add runtime schema validation outside boundaries — TypeScript types are the contract for in-engine calls. Validate only at boundaries: user input, save load, external APIs. The shipped example is `save-validation.ts`, which auto-derives zod schemas from persistent-ref `DefaultValue`s and validates on decode.

## TSDoc Standards

Three tiers based on audience. IDE hover is the primary delivery mechanism — no generated doc site yet.

**Factory functions (`create*()`)** — the consumer's front door:
- One-liner: what it creates, in game-design terms (not implementation terms)
- `@param` for each parameter, with a sentence on the options object's role
- `@returns` describing the returned object's key capabilities
- `@example` with a 5–10 line realistic usage snippet
- Mention related functions if the relationship isn't obvious (e.g., `displayResource` / `resetResource` on `createResource`)

**Public interfaces (Options + Return types)** — the shape consumers configure:
- `/** */` on every field that isn't self-documenting from name + type alone
- **Skip** fields where name + type says it all (`id: string`, `name: string`, `enabled: boolean`). Noise like `/** The ID */` is worse than no doc.
- Focus on *what it controls*, not what type it is (the type signature says that)
- For `MaybeRefOrGetter` fields, note whether reactivity is supported ("can be a ref or getter for dynamic values")

**Enum members** — one-liner per value. Enum names are often cryptic; the doc should say what the value *means* in game terms.

**Internal helpers** (`processGetter`, `topologicalSort`, etc.):
- One-liner explaining *what*, not *how*
- `@internal` tag if exported only for cross-module use
- No `@example` needed

**File headers** — keep the current pattern:
- First line follows the convention `Title — one-line blurb` (em-dash or hyphen with surrounding spaces). The INDEX.md generator uses both: the title becomes the section heading, the blurb appears under it. Without a dash, the whole first paragraph becomes the blurb and the title falls back to the title-cased file stem — fine, but less expressive.
- Module purpose in game-design terms
- Key features as a bullet list
- Cross-references to related modules when non-obvious
- Optional `@cluster <name>` tag joins this file into a named cluster with sibling files in the same layer. Useful when a helper file conceptually belongs to its companion (e.g., `purchasable-category.ts` and `auto-purchase.ts` both declare `@cluster purchasable`; `recommendation-strategies.ts` declares `@cluster recommendation` alongside `recommendation.ts`). Without a tag, files cluster by subdirectory (`src/core/spatial/*.ts` → cluster `spatial`) or stand alone. The tag is the source-local way to express "these belong together"; a small `CLUSTER_OVERRIDES` map in `scripts/lib/source-meta.mjs` exists as an escape hatch when editing the source isn't worth it.

**Do not use:** `@since`, `@deprecated` (pre-1.0), redundant `@see` cross-references, or `@module` tags.

## Quality passes & triage

- **Read before you frame.** Read an abstraction's full source before treating a contract question as an architectural decision — existing optional/polymorphic fields often already answer it. Recorded cross-cuts and codified rules are sanity checks to apply *after* reading, not a checklist to execute; findings drive structure, not the reverse.
- **Substance over surface.** A leaf that produces only banner/TSDoc/naming-nit deltas wasn't worth running. Code-quality findings (dead-surface trims, fixes, primitive simplifications) outrank codification-of-divergence.
- **Best shape is found by comparison.** When auditing "what's the right shape for X?", sweep across `systems/`, `harness/`, `primitives/`, and consumer hand-rolls — not the folder under audit. Resolve divergence by picking the right shape and aligning the laggards (or proving both contexts genuinely differ); never ship both with part tagged "legacy".
- **Audit before answering strict validation.** When a ticket frames multiple zero-adoption surfaces as Path-A/B/C choices, audit real adoption first (load-bearing / calcified / latent contract / aspirational framing); the per-subsystem disposition shape is often the actual finding.
- **Corpus-test ambiguous structure.** For a structural choice (organization axis, taxonomy, boundaries) where iteration isn't converging, spray ~4 subagents (2 sonnet + 2 opus) on the same structural questions with different concrete tasks, briefed not to affirm a prior plan — convergence plus novel ideas beats single-mind iteration.
- **Distill or drop at close.** In-thread codifications (CC-N labels, scoped notes) earn at most a 1–2 bullet code-shape rule here, or get dropped; keep this file light, and no per-folder `CLAUDE.md`.
